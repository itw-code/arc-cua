ARC Index — Vectorless Document-to-Action Engine

Pairing VectifyAI's PageIndex (36k+ stars) with ARC's execution loop on Solari.

The Unified "No-API" Thesis

ARC was founded on the insight that you should not stream the whole UI raster to an LLM; you prune the structure and reason over the tree.

PageIndex (VectifyAI) proves the exact same principle for documents: traditional vector RAG retrieves by semantic similarity, missing structured context. PageIndex replaces vector DBs with a hierarchical tree index where an LLM agent reasons its way through sections like a human expert.

Comparison Matrix

Traditional Stack: Vector RAG (Chunks) + 4K Raster Vision Agent
ARC + PageIndex: Tree Index RAG + Pruned AXTree In-VM Reflex
Concrete Use Case

Autonomous RCM Claim Appeal Flow

What ran live on 2026-09-29, end to end, on a Solari cloud browser:

  1. Ingest: the real PageIndex SDK in local mode builds the document tree (Flash, no PageIndex account; ~9.5 s per document, Gemini 3.8 Flash via LiteLLM).
  2. Reason: PageIndex's agent navigates the tree and answers each schema field with a <cite page/> tag (6–9 s).
  3. Ground: each value is checked against the cited page; uncited, NOT_FOUND, or not-on-page values are rejected and never typed.
  4. Actuate: ARC binds fields to [#N] inputs on a stand-in appeal portal and fills them all in one in-page call (~400 ms), then clicks Submit.
  5. Verify: the portal echoes what it received and renders a random confirmation code; the run grades the echo and matches the scraped code.
Stand-ins: the portal is a local form, not a real payer site. PageIndex citations are page-level (local mode has no layout blocks).

01ColdStart

Aug 31 – Sep 3 2026 · lesson: Check the outcome, not the agent's word
Analogy. A driving test on roads the driver has never seen. Every run reshuffles the town, and the examiner checks where the car actually parked, not what the driver says.
What it is

A harness that generates versions of a small invoice app the agent has never seen, lets a screenshot-driven agent fill it in cold, and checks the resulting database row.

Where the idea came from

My first idea was “Witness”, a verification runtime. My own audit killed it: verification was the most crowded theme, and the “Solari issues” I had cited were other applicants' PRs. I pivoted to zero-shot generalization, aimed at Pinetree's claim that agents can handle apps they've never seen (“Hallucinate Westworld”).

The method

Five ways to change the app, chosen by a seeded random generator: P1 relabel, P2 wizard, P3 field order, P4 navigation, P5 theme. The agent works from screenshots (vision loop). A fail-closed verifier (C1–C7) reads the SQLite row, so “I'm done” from the agent counts for nothing.

How I built it

TypeScript on Solari sandboxes and a Solari browser. An orchestrator ran step-gated subagents: each step wrote a report and was audited before the next began. Tools: Claude Code, Google Antigravity, Pi Coding Agent via OpenCode Go.

What it proved
  • ▸110/110 tests
  • ▸P2 wizard was the one real breaker: 0/2
  • ▸Only 1 of 6 models could finish the form; minimax-m3 got click-locked 24 times
  • ▸Showcase run: 16 steps, 69.4 s sandbox time
  • ▸~175k input tokens over the isolated set
Be honest about

n=2 per axis, so directional only. Not purely vision: clicks are snapped with page.evaluate. 2 of 6 isolated runs aborted on infrastructure. Early ROI figures were mock and are removed.

WHAT IT LED TO → Vision agents were fragile and infrastructure was flaky. I needed to test on a real app, and to test my own claims just as hard.

03ARC CUA

Sep 20 – 29 2026 · lesson: Give the model structure, check every action
Analogy. A restaurant with a numbered menu. Instead of describing a photo of the kitchen, the model just says “number 12”, and the waiter confirms the dish actually arrived.
What it is

A browser harness for agents on Solari: the page becomes a short numbered list of what can be clicked or typed, and every action reports whether the page really changed.

Where the idea came from

The “vision tax”: sending a screenshot on every step is slow and expensive, and ColdStart showed it's fragile. Browser Use's Jev showed that one small call picking {op, index} from a numbered list is enough. I built that pattern on Solari without Jev's API.

The method

The browser's accessibility tree, trimmed to ~1,200 tokens, each actionable item numbered [#N] and pinned to its exact element. Actions return state_changed and stall_suspected, and truncation is announced. Batched fills. An optional reflex policy makes one model call per action.

How I built it

Python over the Chrome DevTools Protocol, shipped as a library and an MCP server (arc-cua-mcp). Built with Claude Code; benchmark runs on Gemini 3.8 Flash on real Solari browsers.

What it proved
  • ▸24/24 vs 21/24 against Solari's own MCP, same model
  • ▸3.8× fewer input tokens, 3.3× cheaper per task
  • ▸Google Flights 3/3 vs 0/3
  • ▸Vs Opus + Solari MCP: 39× fewer tokens, 33× cheaper
Be honest about

The early 99.69% / 2.31 ms / 100% WebArena figures were mock and are now labelled replaced. The in-VM reflex loop doesn't exist yet: it drives the browser over CDP from outside. Not yet at Jev's 7.1 s on Flights (best 16 s).

WHAT IT LED TO → Pages were solved. But real back-office work starts from a document, and the dangerous error there is a wrong value typed in with confidence.

04ARC Index

Sep 29 2026 · lesson: Prove a value before typing it
Analogy. A careful clerk. For every number they copy from a letter, they write down the exact line it came from, and they leave the box blank rather than guess.
What it is

It turns a document (an insurance denial letter) into a verified form fill: every value comes with the row it was taken from, and anything it can't prove is left blank.

Where the idea came from

Pinetree Health's world, revenue-cycle work: a denial letter becomes an appeal in a payer portal. The same thesis as ARC, applied to documents: PageIndex keeps a document's structure as a tree instead of chopping it into vectors.

The method

Index the letter (a PageIndex tree, or pypdf blocks locally). Extract each field with a quote and a citation. Check the cited row: the quote is really there, it's the denied line not the paid one, and only one row fits (the uniqueness rule). Then one batched fill on Solari, and a receipt.

How I built it

A Python package on top of ARC CUA (src/arc_index), also loaded as a plugin by the MCP server. Gemini 3.8 Flash for live runs; Claude Sonnet 5.5 via Claude Code subagents for offline evals, with no API key needed.

What it proved
  • ▸8.4× cheaper per appeal ($0.00305 vs $0.02575)
  • ▸7.8× faster (11.4 s vs 89 s), 22× fewer tokens
  • ▸Same accuracy: 49/60 right, 0 wrong on both sides
  • ▸Wrong values let through on a forced pick: 16 → 0
Be honest about

n=10 appeals and synthetic letters. Sonnet tokens are estimated at chars/4. Block-level PageIndex needs a cloud key. Not yet tested on real payer portals.

Say it in 30 seconds

ColdStart tested whether a vision agent could fill apps it had never seen, and showed it was fragile. A side experiment on Nakama pointed the same checks at a real app, and at my own claims. ARC CUA replaced screenshots with a small numbered view of the page. ARC Index brought the same idea to documents. On the same model and the same Solari browsers, ARC finished 24 of 24 tasks where Solari's own MCP finished 21, at a third of the cost. ARC Index filed the same appeal 8.4× cheaper and 7.8× faster than a normal agent, and never typed a wrong value.

What stayed the same across all four

  • Real infrastructure. Everything ran on Solari: sandboxes, browsers, the real API.
  • Checks outside the model. A database row, a page fingerprint, a cited table row. Never the agent's own “done”.
  • AI builds, I judge. Claude Code and subagents wrote most of the code. I decided what counts as proof.
  • Numbers get replaced, not defended. Mock figures in ColdStart and ARC were removed or labelled once I had live ones.

Words, in plain English

Solari
Cloud computers for agents: browsers, sandboxes and desktops that start in milliseconds, billed per hour.
MCP
Model Context Protocol: a standard way to give a model a set of tools. Solari ships one; ARC ships its own on top.
CDP
Chrome DevTools Protocol: the remote control for a browser. Each message to a Solari browser costs ~186 ms.
Accessibility tree
The browser's own list of what's on the page (buttons, fields, links), the thing screen readers read.
[#N] index
The number ARC puts on each clickable item, so the model can say “click 12” instead of guessing coordinates.
Grounding
Checking that a value really comes from where the model says it does.
Uniqueness rule
If two table rows both fit a field with different values, refuse the field instead of guessing.
PageIndex
Indexes a document as a tree of sections instead of vectors, and gives page and block citations.
SimHash
A fingerprint of the page; if it didn't change after an action, the action probably did nothing.
Fail-closed
When unsure, block. A blank field is safe; a wrong value is not.

What is an accessibility tree and why use it instead of screenshots?cua

It's the browser's own list of what's on the page: buttons, links, fields, with their names. It's what screen readers use. It's text, it's small, and each item can be clicked exactly. A screenshot costs many tokens and the model has to guess coordinates. ARC trims the tree to about 1,200 tokens and gives every actionable item a number like [#12], so the model just says “click 12”.

Proof: src/arc_cua/cdp_extractor.py; token budget in the README
What happens when the page is too big for the budget?cua

ARC says so. The reply carries a truncation notice listing what was cut, and cut items still resolve if the model asks for them. Dialogs, menus and tabs are never cut, so a pop-up can't hide behind a big table. The failure is visible instead of silent.

Proof: truncation_notice in the inspect result
How do you know an action actually worked?cua

Every action reports whether the page really changed (state_changed), whether the page changed on its own since we looked, and after a few no-op actions it flags stall_suspected. “The click returned success” is never treated as done. That's why ARC doesn't loop forever on Google Flights where the plain agent did.

Proof: act result fields; Google Flights 3/3 vs 0/3

What does ARC Index do, in plain words?index

It's a careful clerk. It reads the letter, and for every value it writes down the exact line it came from. Before typing anything into the portal it checks that line: is the quote really there, is it the denied row and not the paid one, and is there only one row that fits. If it can't prove it, it leaves the field blank. Then it fills everything in one go and hands back a receipt.

Proof: src/arc_index/index_bridge.py _check_evidence
What's the dangerous failure you designed for?index

Not a blank field, a wrong value that looks right. On a letter with two denied lines, if you force the model to pick one, the older checks still let 16 wrong values through across 8 runs. The uniqueness rule lets through 0, because it sees two rows that both fit and refuses. Under the normal prompt, Sonnet said AMBIGUOUS itself 8 out of 8 times.

Proof: docs/ARC_INDEX_PLAN.md §10.7; artifacts/benchmarks/offline/
Why PageIndex and not a vector database?index

Because a denial letter is a structured document: sections, tables, rows. Vector search finds text that sounds similar, which is exactly how you pick the paid line instead of the denied one. PageIndex keeps the structure as a tree and gives citations back to page and block, which is what my checks need. Locally I can also run on plain pypdf blocks.

Proof: src/arc_index/pageindex_adapter.py, local_doc_index.py
Why is it 8.4× cheaper than an agent doing the same appeal?index

The agent reads the letter and then walks the portal one tool call at a time, and every call re-sends the conversation. That's 26,955 input tokens and 89 seconds. ARC Index makes one extraction call, runs the checks locally, and fills all fields in one batched browser call: 1,209 tokens and 11.4 seconds. Same accuracy on both: 49 of 60 fields right, 0 wrong.

Proof: artifacts/benchmarks/appeal/summary.json
Why only 49 out of 60 fields?index

The other 11 were left blank, on both sides, instead of guessed. Blank is the safe outcome: a human fills it, and the receipt says which fields were refused and why. The point is that neither side typed a wrong value in the counted runs. In an uncounted trial run, the agent did type a CPT code on the two-denied letter.
